# API выгрузки мерча: `GET /api/merch-sync`

Склад, журнал продаж и перемещения мерча из hjtrack для зеркала в платформе
маркетинга (marketing.herosjourney.kz). Платформа раз в минуту забирает
изменения, хранит копию у себя и строит отчёты по своей базе.

Код: [`api/merch-sync.js`](../api/merch-sync.js), логика — [`api/_lib/merch-sync.js`](../api/_lib/merch-sync.js), тесты — [`tests/merch-sync.test.js`](../tests/merch-sync.test.js) (`npm test`).

> Модель данных сверена с прод-сборкой hjtrack (ticket-tracker-inky.vercel.app)
> на 15.10.2026: в ней есть размеры, возвраты и перемещения, которых нет в
> GitHub-версии. Когда исходники прода появятся в репозитории, сверить ещё раз.

## Почему зеркало, а не готовый отчёт

hjtrack работает на бесплатном тарифе Firebase: 50 000 чтений в сутки на всё
приложение, и в лимит уже упирались — тогда у клубов перестают работать
продажи, графики и чек-листы. Готовый отчёт за месяц читал бы все продажи
месяца на каждый запрос. Зеркало читает только изменения: когда ничего не
происходит, опрос стоит около 6 чтений, раз в минуту — около 8 600 в сутки.

## Доступ

- Только server-to-server. Ключ — в заголовке `x-api-key`, значение —
  переменная окружения `MERCH_API_KEY` в проекте Vercel.
- Ключ в браузер не отдавать: фронт маркетинга ходит к своему бэкенду,
  бэкенд — сюда. CORS у эндпоинта нет специально.
- В ответе есть себестоимость и прибыль (решение от 15.10.2026). Имена
  покупателей, заметки, кассир, продавец и сотрудники в перемещениях не
  отдаются.

## Запрос

```
GET https://ticket-tracker-inky.vercel.app/api/merch-sync?cursor=<из прошлого ответа>&limit=1000
x-api-key: <MERCH_API_KEY>
```

| Параметр | Обязательный | Что это |
|---|---|---|
| `cursor` | нет | Строка `cursor` из прошлого ответа. Без него — полная выгрузка. |
| `limit` | нет | Сколько движений на странице: 1–2000, по умолчанию 1000. |

### Клубы

Поле `club` — строка, как её пишет приложение. На 15.10.2026: `4YOU`,
`COLIBRI`, `VILLA`, `NURLY ORDA`, `PROMENADE`, `EUROPE CITY`, `DUBAI` и
`ГОЛОВНОЙ СКЛАД` — центральный склад, а не клуб: в продажах по клубам его не
показывать, в остатках сети — показывать отдельно. Список не хардкодить,
брать из данных.

### Товары (`products`)

Карточка товара — своя на каждом складе: один и тот же артикул в двух клубах —
две записи с разными `id`. Текущий остаток — поле `stock` (его ведёт само
приложение), а не сумма движений. `sizes` — остатки по размерам, если у
товара размерная сетка, иначе `null`. `isLowStock` = `stock <= minStock`, как
карточка «Мало на складе» в hjtrack. Фото не отдаются.

### Движения (`movements`)

Журнал `merch_sales` в понятном виде.

| `type` | Что это | `qty` | `stockDelta` | `revenue` | `netProfit` |
|---|---|---|---|---|---|
| `sale` | продажа | штук продано | `-qty` | сумма чека | выручка − себестоимость |
| `free` | бесплатная выдача (бартер, приз, маркетинг…), причина в `freeReason` | штук выдано | `-qty` | 0 | −себестоимость |
| `supply` | поставка на склад | штук пришло | `+qty` | 0 | 0 |
| `adjustment` | пересорт (ручная корректировка остатка) | модуль разницы | факт − было | 0 | 0 |

- **Возврат** (`returned: true`, время в `returnedAt`) не удаляет продажу:
  запись остаётся, `qty` и `unitPrice` — как в исходной продаже, а `revenue`,
  `netProfit` и `stockDelta` обнулены, потому что деньги и товар вернулись.
  Так же считает и само приложение. Поэтому `SUM(revenue)` сразу даёт
  выручку без возвратов. Сумма возвратов — `qty × unitPrice` по записям с
  `returned`.
- `size` — размер, если товар с размерной сеткой.
- `paymentMethod` — только у `sale`: `Kaspi`, `Наличные`, `Карта`.
- `buyerType` — у `sale` и `free`: `client` или `employee` (продажа сотруднику по своей цене).
- `unitCost` — себестоимость на момент операции. Если товар завёл менеджер
  клуба, а шеф ещё не проставил себестоимость, там 0 и прибыль равна выручке.
- `club` может быть `null` у очень старых записей.
- Время — ISO 8601 в UTC. Дни и месяцы для отчётов считать по Алматы (UTC+5).

### Перемещения (`transfers`)

Перемещения товара между складами (`merch_transfers`). Остатки в `products`
уже учитывают их сами; список нужен, чтобы показать товар «в пути».

- `pending` — товар уже списан у `fromClub`, у `toClub` ещё не появился.
- `accepted` — принят; `receivedQty` может быть меньше `qty` (недостача при
  приёмке).
- `rejected` — отклонён, товар вернулся к `fromClub`.

### Удаления (`deleted`)

Приходят только в ответах с курсором: id удалённых товаров и продаж из
журнала `merch_history`. Чтобы удаление продажи опознавалось, приложение
должно писать в журнал `saleId` — эта правка есть в этой ветке, но в
прод-код её ещё нужно перенести. До тех пор удаления продаж видны только
через полную выгрузку. Возвраты от этого не зависят: они приходят как
обновлённые движения.

## Как опрашивать

1. **Первый запуск.** Запрос без `cursor`. Пока `hasMore: true` — сразу
   повторять с новым `cursor`. Сохранить последний `cursor`.
2. **Каждые 60 секунд.** Запрос с сохранённым `cursor`; если `hasMore` —
   дочитать страницы сразу. Применять в порядке: upsert `products`,
   `movements` и `transfers` по `id`, затем удалить `deleted`. Сохранить
   новый `cursor` только после того, как изменения записаны в базу.
3. **Раз в сутки ночью** — полная выгрузка без `cursor`, и заменить зеркало
   целиком. Она подбирает то, что дельта не видит: удаления продаж без
   `saleId`, возвраты с сильно сбитыми часами на устройстве, правки базы
   скриптами в обход приложения.

Полную выгрузку не делать чаще раза в сутки: она читает весь журнал продаж
и тратит общий лимит Firebase.

Одни и те же записи могут приходить повторно — это нормально, upsert по `id`.
Возвраты и перемещения в течение 15 минут после события приходят в каждом
опросе (запас на расхождение часов устройств). Ответы с одним и тем же
курсором тоже можно повторять: если запись в базу маркетинга упала, просто
повторить запрос со старым `cursor`.

## Ошибки

| Код | Когда |
|---|---|
| `400` | битый `cursor` или `limit` вне 1–2000 |
| `401` | нет ключа или ключ неверный |
| `405` | метод не `GET` |
| `500` | Firestore не ответил (например, исчерпан лимит) — повторить позже |
| `503` | на сервере не задан `MERCH_API_KEY` |

## Как это работает внутри

- Курсор хранит четыре метки: время чтения товаров, время чтения журнала
  удалений, время для поиска возвратов и перемещений и позицию последнего
  отданного движения (время создания + id). Метки берутся из Firestore, а не
  из часов сервера, поэтому запись, закоммиченная после чтения, всегда
  попадает в следующий ответ.
- Товары в дельте — те, у кого `updatedAt` позже метки; приложение
  обновляет `updatedAt` при любой продаже, возврате, поставке, пересорте,
  перемещении и правке.
- Движения листаются по `createdAt` и id, так что записи с одинаковым
  временем не теряются на стыке страниц.
- Возвраты и перемещения приложение помечает временем по часам браузера
  (`returnedAtISO`, `createdAtISO`, `resolvedAtISO`), поэтому их ищем от
  метки минус 15 минут.
- Составные индексы не нужны: каждый запрос фильтрует и сортирует по одному
  полю, а сортировку по id документа Firestore добавляет к такому индексу сам.

## Запуск

1. В Vercel (проект `ticket-tracker`, ticket-tracker-inky.vercel.app)
   добавить переменную `MERCH_API_KEY` — длинную случайную строку, например
   `openssl rand -hex 32`. Переменные `FIREBASE_*` уже есть, их используют
   другие эндпоинты.
2. Перенести эту ветку на актуальный прод-код и задеплоить.
3. Проверить:
   ```bash
   curl -s -H "x-api-key: $MERCH_API_KEY" "https://ticket-tracker-inky.vercel.app/api/merch-sync?limit=5"
   ```
4. Тот же ключ положить в секреты бэкенда платформы маркетинга.
